# Feature UX

What a screen shows, in **every** state, including the ones nobody wants to draw.

The house rule: a feature is not designed until its loading, empty, conflict and
failure states are written down. Those four are where a user meets the system on
their worst day, and they are what gets improvised at the end of the sprint if
they are not decided at the start.

Wording for a failure the API already named belongs to the API, not to the
screen. That is written down here because it is the rule teams most often break,
and every time they break it the same error ends up worded three ways in three
clients.
